# 简历生成

## 快速开始

1. 先确认信息来源：历史 PDF、Word、Markdown、截图、链接，或只基于对话信息。
2. 判断信息是否达到“可生成标准”。如果不足，必须先提问补齐；不要先生成含大量占位符的简历草稿。
3. 信息仍不足时，持续分轮追问，每轮只问最关键的 3-6 个问题，直到达到可生成标准或用户明确要求先用占位内容。
4. 达到可生成标准后，确认输出类型：完整版简历、精华亮点版简历，或两者都要。
5. 确认目标岗位、候选人阶段和 UI 风格后，再生成 HTML。
6. 先生成 Markdown 内容，再生成 HTML 预览，最后必须等用户明确认可后才能导出 PDF。

## 核心原则

- 旧简历只作为信息来源，不直接照搬格式；先提取信息、判断问题，再重新组织表达。
- 不默认套用固定叙事，比如“负责人视角”；要根据候选人阶段、资历、目标岗位和经历判断重点，必要时向用户确认。
- 保持内容真实，只优化结构、表达、重点和敏感信息处理方式。
- 用户未确认 HTML 预览前，不生成最终 PDF。
- 当用户信息不足以支撑简历时，不要编造公司、学历、项目、年限、成果或联系方式；先追问补齐。
- 生成 PDF 后，必须通过实际查看或等效方式检查结果，再向用户汇报。

## 信息收集

如果用户提供 PDF、Word 或 Markdown 简历，要提取以下信息：

- 基本信息
- 照片文件路径或明确不使用照片
- 教育经历
- 工作经历
- 项目经历
- 技能清单
- 可量化成果
- 与目标岗位相关的信号
- 敏感或内部表述

如果信息不完整，必须先提问补齐，不要直接生成占位符过多的草稿。

### 可生成标准

只有同时满足下面信息后，才开始生成简历内容：

- 基本信息：姓名、目标岗位、候选人类型至少明确；联系方式和城市如果缺失，先询问，用户拒绝提供时可留空。
- 照片：必须询问用户是否需要放照片；如果需要，要求提供本地图片路径、`file://...` 地址或可访问的图片地址；如果不需要，记录为“不使用照片”。
- 教育经历：至少有学校/学历/专业/时间范围中的 3 项；如果用户明确说暂不写教育经历，可跳过。
- 工作经历：社招候选人至少有 1 段公司/岗位/时间范围/主要职责；校招或实习候选人至少有 1 段实习、项目或校园经历。
- 项目经历：至少有 1 个项目的背景、本人角色、关键工作；如要写 AI Agent 岗位，必须知道至少一个相关项目、工具链或实际能力证据。
- 技能清单：至少知道主要编程语言、AI/LLM 相关能力、工程框架或工具中的若干项，足够按类别描述。
- 输出偏好：完整版、精华亮点版或两者都要；UI 风格如果用户没说，可给 2-3 个选项让用户选。

### 信息不足时的追问方式

每轮最多问 3-6 个最关键问题，按缺口优先级提问：

1. 先问会决定简历定位的问题：目标岗位、候选人类型、年限/阶段、希望投递方向。
2. 再问硬事实：联系方式、城市、是否使用照片及照片文件路径、教育经历、工作公司、岗位、时间。
3. 再问可写出竞争力的内容：代表项目、本人做了什么、用了什么技术、结果或影响。
4. 最后问输出形式和 UI 风格。

如果用户只给出“姓名 + 岗位 + 模糊经历”（例如“王五，社招 AI Agent 开发，之前在某互联网公司工作”），必须继续追问，不能开始生成正式 Markdown/HTML。

### 允许先生成草稿的例外

只有在用户明确说“先用占位符”“信息不全也先生成”“你自己假设”等类似表达时，才可以生成带明显待补充标记的草稿。即便如此，也不得编造具体公司、学校、项目数据、量化结果或联系方式。

## 候选人定位规则

根据用户提供的事实选择表达重点：

- 社招负责人/TL：突出负责范围、体系建设、跨团队推进、业务影响和结果闭环。
- 社招独立贡献者：突出模块负责、难题解决、技术深度和稳定交付。
- 校招生/实习生：突出基础能力、项目完整度、学习能力、工程习惯和成长潜力。
- 转行候选人：突出可迁移能力，以及过往成果和目标岗位之间的连接。
- 管理者：突出团队建设、规划能力、资源协调和结果负责。

如果定位会明显影响简历措辞，要让用户确认。

## 输出流程

### 完整版简历

用于正式投递和面试准备。内容应包含基本信息、教育经历、工作经历、个人简介、核心优势、项目经历和技能清单。项目经历建议按背景、角色/定位、关键工作、结果来组织。整体要完整，但不要冗长。

“技能清单”必须分类描述，不要写成一整行关键词。分类要根据候选人和目标岗位选择，例如：编程语言、AI/LLM 框架、前后端框架、数据与存储、云服务/工程效率、安全、产品/管理/协作、工具等。每一类都要简短说明候选人能用这些技能做什么，而不只是堆关键词。

完整版简历默认布局如下：

- 如果是社招候选人，工作经历放在最前面。
- 教育经历。
- 个人简介。
- 项目经历。
- 其他部分，例如核心优势、技能清单、团队影响、论文、奖项等，可根据需要放在后面。

除非用户明确要求调整布局，否则不要改变这个默认顺序。

### 精华亮点版简历

用于手机预览、招聘方快速浏览、面试前快速扫描或作品集式展示。重点放在候选人定位、关键数据、最多 3 个代表项目、能力标签和联系方式。它不是完整版简历的简单压缩，而是一份价值摘要。

精华亮点版默认要区分两个交付版本：

- 手机版：用于手机阅读和转发，页面宽度按手机视觉设计，导出的 PDF 也必须使用手机页面尺寸；内容要贴合页面，不要出现 A4 页面中间一条窄长内容、上下大面积留白的问题。
- PC 版：用于电脑浏览、横向展示或网页投放，页面应按桌面宽度撑满主要可视区域；导出的 PDF 也要匹配桌面页面宽度，不要只使用手机窄版居中。

如果用户只说“精华亮点版”，默认同时生成手机版和 PC 版，除非用户明确只要其中一种。文件名建议分别带上 `手机版` 和 `PC版`。

## HTML 和 PDF 确认流程

必须按下面顺序执行：

1. 生成 `resume.md` 或 `resume-highlight.md`。
2. 内容方向确认后，生成 `resume.html` 或 `resume-highlight.html`。
3. 向用户说明 HTML 路径、UI 风格和输出类型，并询问是否认可导出 PDF。
4. 只有用户明确说“认可”“可以”“确认”“生成 PDF”“导出 PDF”等，才生成 PDF。
5. 如果用户要求修改，先更新 HTML，再重新询问；不要提前导出 PDF。

## UI 风格规则

先让用户选择或提供参考。常见风格包括：Apple 极简、黑白专业、暖色手绘、科技作品集、ATS 传统简历、参考图片风格等。

用户也可以提供本地 HTML 路径或 `file://...` 页面链接作为 UI 参考。遇到这种情况时，尽量实际查看参考页面，并参考它的整体节奏、字体、间距、颜色、卡片、边框和层级关系；但不要复制无关内容，要保持简历清晰、专业、易读。

如果要生成手机预览类 PDF，可参考 [REFERENCE.md](REFERENCE.md)。需要用 Chrome 导出 PDF 时，优先使用 [scripts/export_pdf_chrome.sh](scripts/export_pdf_chrome.sh)。

## 最终检查清单

向用户汇报前，必须确认：

- 输出文件存在，并能提供完整路径。
- 如果用户选择使用照片，照片文件路径存在或图片地址可访问；如果不使用照片，简历版式不预留突兀空位。
- PDF 页数合理。
- 精华亮点版如果有手机版和 PC 版，两种 PDF 的页面尺寸要分别符合手机和电脑阅读场景。
- PDF 没有浏览器默认页眉页脚。
- 没有明显空白页，也没有最后一页大面积空白。
- 每页顶部留白正常，背景或装饰连续。
- 中文、联系方式、日期、照片和关键信息显示正常。
- 如果使用照片，照片应放在姓名右侧或顶部合适位置，大小自然，不挤压姓名、目标岗位和联系方式。
- 图片正常加载，不遮挡文字。
